# Milestone v1.1 Decision Record: Open Enhancement Hardening

**Decided:** 2026-07-10
**Basis:** Source-verified commercial-capability inventory (`.planning/research/CAPABILITY-MATRIX.md`, 53 capabilities, evidence at revision `508403749`) plus an adversarial completeness critique.

## Question

With v1.0 shipped (4 domains, release candidate, 20 UAT pending) and no proprietary shortcuts allowed, what is the lowest-risk, clearest-dependency, real-value next milestone that can be fully verified without a second VPS or third-party account?

## Evidence that constrained the choice

1. **`uiGateOnly = ∅`.** Seven independent source probes found **no** marketed commercial capability that is merely a frontend/license gate over a complete OSS backend. There is no "flip the flag" win. Only 4 rows are already fully open (`none_exists_full`: website backup, website restore, API allowlist, advanced theme) and those are not gaps.
2. **Every real feature needs new backend/data-model work**, and the five heaviest clusters (multi-node, WAF, anti-tamper, DB-HA, VM) are each a **separate security domain** requiring a second real VPS / KVM host to UAT — neither available, and the project forbids bundling them.
3. **Multi-node registration is the keystone** (15+ capabilities depend on it) but is XL, `critical` network risk, needs SSH/TLS cross-host mutual auth and a threat model first. Not a safe first step.
4. **Two concrete, source-grounded debts already exist in shipped v1** (independently verified — see below), and adding surface on top of them compounds risk with no regression coverage.

## Grounding the two debts in real source (not assumed)

The completeness critique correctly flagged that these two debts were **not** in the probe evidence — because the probes were scoped to *unimplemented commercial capabilities*, not *shipped v1 features*. They were therefore verified directly:

- **Webhook secret at rest is plaintext.** `agent/app/service/alert.go:531` (`upMap["config"] = req.Config`) and `:538-543` (create via `copier.Copy`) persist the webhook URL with no encryption; masking (`maskWebhookAlertConfigs`, `:551`) is applied only on API output. The URL is a bot secret and lands plaintext in the alert DB and its backups. 1Panel already encrypts other secrets at rest with `encrypt.StringEncrypt/Decrypt` (`agent/app/service/backup.go:196,200`; `database.go:367`) — the house pattern the webhook field simply skipped.
- **`AIAgentLimit` enforcement is a check-then-act race with no UI.** `agent/app/service/agents.go:146-155` reads the count, then `:307` creates the row after the entire slow `installWithHooks` — no lock/transaction spans them, so concurrent creates both pass. `agents.go` has no UI surface; the value is only settable via the raw setting API (`setting.go:128`).

## Decision

**v1.1 = Open Enhancement Hardening**, scoped to exactly these two shipped-feature debts, delivered as **two independent phases** (one security domain each), both fully CI/Go-testable in WSL with Go 1.26.1, needing no VPS / second host / third-party account:

- **Phase 06 — ALERT-SEC-01:** encrypt the webhook URL at rest using the repo's existing `encrypt.StringEncrypt/Decrypt`, with a transparent migration for existing plaintext rows; keep API masking and edit-preserve; never log or return the secret.
- **Phase 07 — AGENT-02:** make `AIAgentLimit` enforcement race-free via a mutex-guarded slot reservation (reads the committed count inside the lock + tracks in-flight reservations, without holding the lock across the install), and add the missing management UI control wired to the existing validated setting endpoint.

## What the critique changed (accepted revisions)

The synthesis originally proposed a **three-workstream** v1.1 (secret-encryption + capability-registry + UAT-automation). The critique's strongest point — that this bundles unrelated domains, ships zero user-visible value, and rests on an undecided key-management design — is accepted:

- **Dropped: capability-registry.** Premature generalization; an abstraction over commercial capabilities before enough exist to validate it. Revisit when ≥3 capabilities need consistent registration.
- **Demoted: UAT-automation.** Not a headline deliverable. Each phase carries the mandated negative-path focused tests instead. Authored (not executed) browser UAT scripts may be added to burn down debt, but never claimed as executed without a running panel.
- **Neutralized: key-management "undecided" risk.** There is nothing to decide — reuse the existing DB `EncryptKey` + `encrypt.StringEncrypt`, identical to how `backup.go`/`database.go` already store secrets. Clean-room and consistent.
- **Kept the P0 keystone deferred, on purpose.** The critique flags that deferring multi-node delays the highest-priority work. True, but multi-node is untestable without a second VPS and unsafe without a threat model; shipping unverified distributed auth would be the worst outcome for a security-sensitive control plane. It is sequenced as its own threat-modeled milestone, not skipped.

## Alternative considered (and why it is v1.2, not v1.1)

**Branding + custom-login + advanced-theme** (all `fitNextMilestone=true`, backend depends only on the open enhancement-setting service already extended in v1.0). Attractive and visible, but it introduces **file upload** (logo/favicon/background) and **pre-authentication rendering**, demanding rigorous negative-path validation and a pre-login public-safe subset. Sequencing hardening first lets branding land as a fast, low-risk follow-on on a base whose secret-at-rest and concurrency debts are already paid. Branding is the planned v1.2.

## Sequenced roadmap after v1.1

1. **v1.1** Open Enhancement Hardening (this milestone).
2. **v1.2** Branding / white-label / custom-login (enhancement-setting cluster; single-node; file-upload + pre-auth safe subset).
3. **v1.3** Threat-modeled secure multi-node enrollment + Core↔Agent mutual auth (keystone; needs 2nd VPS for UAT).
4. Thereafter, each as its own security milestone: advanced WAF, website monitoring, anti-tamper, RBAC, ops reports, AI platform (model dir → vLLM → gateway/benchmark/Skills Hub), database HA, virtual machines.
