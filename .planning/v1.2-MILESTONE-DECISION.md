# Milestone v1.2 Decision Record: Open Branding Text & Login Colors

**Decided:** 2026-07-11
**Basis:** Source-verified branding design + adversarial threat model (`.planning/research/BRANDING-DESIGN.md`, workflow `wgegzscqj`, 6 agents).

## Question

The capability inventory named branding/custom-login as the sequenced next milestone (v1.2). How much of it can be shipped as a safe, real, fully CI-verifiable increment without a VPS?

## Evidence

- The enhancement DTO already declares all 9 branding fields (`dto/enhancement.go:3-16`) but the service never populates them; the frontend already consumes them pre-auth via the public endpoint (`use-logo.ts` → `/enhancements/public`). So the render path is community-wired.
- The image **serve** endpoint already exists (`router.go:114 RegisterImages`), but **no upload endpoint exists**, and the serve path force-serves `<svg>` as `image/svg+xml` — a critical pre-auth stored-XSS vector (T1/T2).
- The branding **editor** lived in the absent xpack overlay; community has no edit form, so the feature is unsettable without one.
- The adversarial threat model returned `design_sound` with a decisive recommendation: **ship P1 (text/color) only**; defer P2 (login text — its XSS control lives in Vue, not Go CI) and P3 (image upload — needs serve-side SVG hardening, `DecodeConfig` dimension caps, CSRF verification, `.ico` resolution).

## Decision

**v1.2 = "Open Branding Text & Login Colors" — P1 only**, delivered as two phases (both text/color, **no file upload**, no new attack surface):

- **Phase 08 — BRAND-01 (CORE backend):** wire `Title, MasterAlias, LoginBgType, LoginBackground(color), LoginBtnLinkColor` through the existing seam — validator cases (reject `<>`/control chars + rune caps for text; `oneof` for bg-type; `isSafeCSSColor` for colors; empty = unset), populate the authenticated getter, widen the anonymous subset with a **strict subset-assertion test**, extend the write `oneof`. The XSS control (T7) is server-side and fully Go-testable; the anon-surface control (T8) is the subset test.
- **Phase 09 — BRAND-02 (frontend):** a minimal community settings form for those five fields, wired to the existing open update endpoint, rendered as textContent. `build:pro` + ESLint verified; browser visual is human UAT.

## Deliberately deferred (with the threat model already captured)

- **v1.3 = image branding upload** (logo/favicon/loginImage/loginBackground image): the single high-risk build item. Must honor T1–T6, T9, T10 from `BRANDING-DESIGN.md` — especially serve-side SVG hardening bundled in the same change, `MaxBytesReader`, `DecodeConfig` dimension cap, fixed-enum filenames, CSRF verification, and the `.ico` decision.
- **Login welcome/subtitle/copyright text (P2):** foldable into v1.3 or its own phase; primary control is the same server-side reject-`<>`, rendered as interpolation.

## Why not bundle it all

Bundling the from-scratch multipart upload (arbitrary-file-write + stored-SVG-XSS surface) with pure text wiring repeats the anti-pattern the v1.1 critique flagged. P1 is a complete, usable, low-risk, world-verifiable increment on its own; sequencing the upload as its own hardened milestone is strictly safer.

## Security acceptance (this milestone)

Widening the anonymous endpoint to expose the cosmetic set (brand title, alias, login colors, bg-type) is REQUIRED for pre-auth rendering and is accepted: these are non-secret display values that inherently appear on the login page. The subset-assertion test guarantees no path/watermark/version/secret data joins the anon surface.
