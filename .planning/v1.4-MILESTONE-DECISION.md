# Milestone v1.4 Decision Record: Open Login-Page Text (+ login-hero render fix)

**Decided:** 2026-07-11
**Basis:** Live v1.3 VPS UAT (2026-07-11) closed the branding-image loop and surfaced one gap (`LOGIN-HERO-RENDER`). The remaining deferred branding slice is **P2 login-page text**, captured in `.planning/v1.2-MILESTONE-DECISION.md` and `.planning/research/BRANDING-DESIGN.md` (T7). This milestone ships P2 plus the login-hero fix.

## Question

v1.2/v1.3 delivered branding text, colors, and image upload. The last documented branding slice is **login-page text** (welcome / subtitle / copyright). And the live v1.3 UAT found the community login page doesn't display an uploaded login image/background due to a frontend preload-timing bug. What is the safe, CI-verifiable increment?

## Decision

**v1.4 = "Open Login Page Text" + the `LOGIN-HERO-RENDER` fix**, one phase:

- **Phase 12 — LOGIN-TEXT-01 (backend + frontend):** wire three operator-authored login-page text fields through the existing enhancement seam:
  - `LoginWelcome`, `LoginSubtitle` (≤128 runes), `Copyright` (≤200 runes).
  - **Reuse the v1.2 text control (T7):** `validateBrandingText` rejects `<>` and control characters and caps runes — the server-side half; the login page renders them as **interpolation (`{{ }}`), never `v-html`** — the client half. This is the exact pattern the threat model prescribed for P2 (do NOT reuse the raw-HTML welcome mechanism).
  - Populate the authenticated getter; widen the anonymous subset (the login page needs them pre-auth); extend the write `oneof`; strict-subset test updated.
  - Frontend: render welcome/subtitle at the top of the login card and copyright as a footer (interpolation); add three inputs to the community branding form; i18n zh+en.
- **Bundled fix — `LOGIN-HERO-RENDER`:** `login/index.vue` now preloads the uploaded loginImage/loginBackground **reactively** (a `watch` on `themeConfig`, immediate) instead of a one-shot `onMounted` read, so the custom login image/background actually appear once the public settings populate. Discovered in the v1.3 live UAT.

## Security acceptance

- Login text is non-secret display content that inherently appears on the login page; widening the anon subset with it is accepted (same posture as v1.2 title/colors). The subset-assertion test proves no watermark/paths/bytes/versions join the anon surface.
- The primary XSS control is server-side (`validateBrandingText`); markup can never be persisted, so the login page cannot render injected script regardless of client rendering. Interpolation is the second layer.

## Deliberately out of scope

- Rich/multi-line login text or HTML — plain single-line text only (control chars rejected).
- v1.5+ secure multi-node (the keystone; needs a full threat model + a second VPS).
