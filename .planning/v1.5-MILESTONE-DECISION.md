# Milestone v1.5 Decision Record: Secure Multi-Node (Enrollment + PKI + Node UI)

**Decided:** 2026-07-12
**Basis:** The branding cluster (v1.2–v1.4) is feature-complete. v1.5 opens the **keystone** the 15+ commercial capabilities depend on. Grounded in `.planning/research/NODE-ENROLLMENT-DESIGN.md` (triangulated by 4 source probes: node-registration map, agent-side auth/listen, core↔agent transport, frontend node surface). This is a **security feature**, so per project doctrine the enrollment/PKI is REAL — no flag-flip no-op.

## Question

The community source ships a **hollow mTLS shell** for remote nodes: the two-mode listener, `RequireAndVerifyClientCert`, encrypted `ServerCrt/ServerKey/RootCrt` settings, `Proxy-Id` binding, socket routing, the `CurrentNode` header interceptor, and the node switcher UI all exist — but every piece that makes remote federation a *security feature* (CA issuance, enrollment handshake, real per-node cert pinning, the core-side mTLS client transport, the node-management pages) is a closed-source stub. What is the safe increment, and how far does v1.5 go?

## Decision

**v1.5 = Slice A (backend PKI + enrollment) + Slice B (community node UI).** Slice C (cross-network live acceptance) is deferred — no second VPS available — and tracked as human UAT debt. **Completion standard for v1.5 = single-box loopback mTLS end-to-end verification** (unit tests for all crypto/token paths + an in-process mTLS handshake test proving mutual auth + fingerprint pin + wrong-cert rejection). Three phases:

- **Phase 13 — Node registry + CA/PKI + enrollment token (backend core, unit-tested):**
  - `nodes` registry: model + migration + service + authenticated CRUD API (SessionAuth + CSRF, the enhancement/setting posture). Implement the read endpoints the frontend **already calls but core lacks**: `POST /core/nodes/list`, `GET /core/nodes/simple/all` (shapes per `frontend/src/api/interface/setting.ts:311-334`).
  - CA management: core owns the private CA (generate/load, encrypted at rest); sign per-node leaf certs from a CSR; SHA-256 DER fingerprints.
  - Enrollment token: issue + redeem with **N1** single-use (atomic burn), **N2** HMAC-SHA256 authentication (constant-time), **N3** nodeId-scope + ≤10-min TTL, **N4** master-fingerprint embed. Unit tests: replay / forgery / expiry / tamper all rejected.
- **Phase 14 — Real mTLS proxy + agent cert validation + node bootstrap (backend, loopback-verified):**
  - Core `MultiNodeProvider.Proxy` + `LoadNodeInfo`: dial `https://addr:NodePort` with a **CA-verifying, per-node-fingerprint-pinning, client-cert-bearing** transport (**N5/N8/N12/N14**); registry-derived target only.
  - Agent `ValidateCertificate`: pin the master client-cert fingerprint + honor `Proxy-Id` (**N6/N7**); the enrollment endpoint gate (**N13**).
  - Agent node bootstrap: generate keypair + CSR, call core enroll (pinning master fingerprint), persist returned `ServerCrt/RootCrt` + write `Proxy-Id`; private key never transmitted (CSR pattern, **N9**).
  - Single-box loopback integration test exercises the full mTLS handshake + pin on 127.0.0.1.
- **Phase 15 — Community node management UI + honest re-gate (frontend):**
  - Re-create the missing lifecycle: an add-node / enroll wizard, list, remove/revoke — real `src/views/...` routes, reusing the present switcher/drawer/`<NodeSelect>`/`CurrentNode` interceptor.
  - **Honest gate (doctrine):** re-gate the community node UI on a genuine signal (≥1 enrolled node / a community capability flag), **never by forging `isProductPro`/license** (`store/modules/global.ts:101-103`). Same posture as the branding community forms.

## Security acceptance

- The enrollment path is authenticated by a real single-use HMAC token binding one node + embedding the master fingerprint (no TOFU); the core→node channel is real mTLS with per-node fingerprint pinning (CA-chain validity alone is insufficient). The N1–N15 controls in the design doc are the acceptance checklist.
- We never regress the single-host posture: production default stays `master` (unix socket); node mode is opt-in via a provisioned node install.
- Honest UAT: cross-network enrollment over the public internet needs a second host — **deferred, tracked as human UAT debt** (consistent with prior milestones); it will NOT be marked passed without a real two-box run.

## Deliberately out of scope

- **RBAC / multi-user** (`AuthProvider.CoreRBACMiddlewares` nil) — separate commercial domain; not required for single-admin multi-node.
- `Sync` / `AutoUpgradeWithMaster` / `PushSSLToNode` / `ProxyDocker` / `UpdateGroup` / `CheckBackupUsed` — federation conveniences layered later.
- Scheduled auto cert rotation (expiry + manual revoke ship now; auto-rotation later).
- Cross-network live acceptance (Slice C) — needs a second VPS.
