# Milestone v1.3 Decision Record: Open Image Branding Upload

**Decided:** 2026-07-11
**Basis:** Source-verified branding design + adversarial threat model (`.planning/research/BRANDING-DESIGN.md`), re-verified against HEAD `72e9fab31` before implementation.

## Question

v1.2 shipped the safe text/color slice of branding and explicitly deferred the single high-risk item: **image upload** (logo, logo-with-text, favicon, login image, login background image). v1.3 delivers it — the first from-scratch multipart file-write surface in the project — under the captured threat model. How is it built so that every control in T1–T10 is honored and CI-verifiable without a VPS?

## Evidence (re-verified at HEAD `72e9fab31`)

- **The frontend already models these as presence-sentinel + fixed served path**, not bytes:
  - `Sidebar/.../Logo.vue:5-6,15-16` renders `<img v-if="themeConfig.logo" :src="/api/v2/images/logo?t=…">` (and `logoWithText`) — value only needs to be truthy; bytes come from the fixed anon serve path.
  - `utils/xpack.ts initFavicon:48,61` probes `/api/v2/images/favicon?t=…` gated on `if (favicon)` truthiness.
  - `views/login/index.vue:64-86,98-104` uses **exact-match sentinels**: `loginImage === 'loginImage'` and `loginBackground === 'loginBackground'` trigger preload of `/api/v2/images/{loginImage,loginBackground}`.
  - So the canonical stored value for each image field is the **literal camelCase key sentinel** (`logo`, `logoWithText`, `favicon`, `loginImage`, `loginBackground`). No path, no version, no bytes ever leave the settings table.
- The image **serve** endpoint exists (`router.go:114 RegisterImages`) and force-serves any body containing `<svg` as `image/svg+xml` (`router.go:133`) — the critical pre-auth stored-XSS vector (T1/T2). **No upload endpoint exists.**
- CSRF is already global: `middleware.CSRFTokenGuard()` (`router.go:94`, `middleware/csrf_protect.go:39-60`) enforces a valid `X-CSRF-Token` header on every non-safe method under `/api/v2/` with a session cookie. Any new authed POST under `PrivateGroup /api/v2/core` inherits it (T9 satisfied by construction). The frontend axios interceptor injects the header from the `pcsrftoken` cookie on every request (`api/index.ts:59-62`), including multipart.
- Decoders in reach with **no new dependency**: stdlib `image/png`,`image/jpeg`,`image/gif` + already-present `golang.org/x/image/webp` (indirect, `go.mod:120`). No stdlib `.ico` decoder → **T10 resolves to PNG-only favicon**.
- `LoginBackground` is dual-use: a color hex (bg-type=color) **or** the image sentinel `loginBackground` (bg-type=image). The validator's color-only case must additionally accept that one sentinel, or the read-path re-validation (`loadValidatedEnhancementValue`) would strip it.

## Decision

**v1.3 = "Open Image Branding Upload"**, delivered as two phases:

- **Phase 10 — BRAND-IMG-01 (CORE backend):**
  1. **Serve-side hardening (T1/T2), REQUIRED and bundled here:** rewrite `RegisterImages` — remove the `<svg>` force-override; set Content-Type from an **image allowlist** (`http.DetectContentType` constrained to png/jpeg/gif/webp/bmp/x-icon, else `application/octet-stream`); always emit `X-Content-Type-Options: nosniff`. Serve-side sniff safety does not depend on upload validation.
  2. **Upload endpoint** `POST /settings/enhancements/asset` (authed + PasswordExpired + global CSRF): fixed server-side `assetKey` enum → hardcoded basename/settingKey/size-cap/require-PNG (never client `Filename`, T3); `http.MaxBytesReader` before parse + per-key size cap (~2 MB general, ~256 KB favicon, T4); reject SVG by magic-byte scan; `image.DecodeConfig` format whitelist + `width*height ≤ 16 MP` reject **before** full `image.Decode` (T5); atomic `os.CreateTemp`+`Rename` into `uploads/theme/<assetKey>` with a `filepath` prefix assertion (T3/T6); persist the sentinel setting.
  3. **Reset endpoint** `POST /settings/enhancements/asset/reset` (same guards): remove the fixed basename (exact name, no glob, T6) + clear the setting.
  4. **DTO/validator:** populate `Logo/LogoWithText/Favicon/LoginImage` in the authenticated getter; widen the anonymous subset with those four **presence sentinels** (T8-endorsed presence flags — the images are already world-readable at `/api/v2/images/*`, so a sentinel leaks nothing new; watermark/paths/bytes/versions stay out, asserted by the updated subset test); validator gains fixed-sentinel cases for the four image keys and the `LoginBackground` image sentinel. The image keys are **not** added to the `/enhancements/update` write `oneof` — they are settable only through the upload/reset service.
- **Phase 11 — BRAND-IMG-02 (frontend):** upload + reset controls for the five image assets in the community branding form; `loginBackground` upload shown only when bg-type = image; multipart via the normal api client (CSRF auto). `build:pro` + ESLint verified; browser visual + pre-auth render are human UAT.

## Security acceptance (this milestone)

- The anon subset gains only cosmetic **presence sentinels** for assets that are already anonymously fetchable through the pre-existing `/api/v2/images/*` route; no new byte/path/version/secret is exposed. The subset-assertion test is updated to prove watermark and any non-cosmetic key still never appear.
- Removing the `<svg>` serve override is safe in the open build: nothing in the community build serves an SVG through `RegisterImages` (the favicon fallback is `/public/favicon.png` or an inline `data:` URI built client-side in `getColoredFavicon`, never the theme dir), and uploads reject SVG. Documented as an explicit sign-off.

## Deliberately deferred

- **Login welcome/subtitle/copyright text (P2):** not folded in — keeps v1.3 focused on the file-upload surface. Its control is the same server-side reject-`<>`; sequence it as its own small phase after v1.3 accepts.
- **`.ico` favicon:** rejected by design (no stdlib decoder); PNG favicon only. Revisit only if a real need appears with a vetted ICO validator.

## Why its own milestone

Bundling a from-scratch multipart write (arbitrary-file-write + stored-SVG-XSS surface) with anything else repeats the anti-pattern the v1.1 critique flagged. Isolated, every control is testable and the blast radius is one review.
