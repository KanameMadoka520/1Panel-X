# Milestone v1.6 Decision Record: Website Access Monitoring (WAF domain, feasible half)

**Decided:** 2026-07-13
**Basis:** Two source probes into the "WAF / website monitoring" domain (`.planning/research/WEBSITE-MONITORING-DESIGN.md`). The WAF engine (1pwaf/OpenResty Lua) is **absent** from the tree (closed app); website access-analytics is greenfield but buildable from the existing nginx `access.log` + the host-monitor time-series template + the already-present GeoIP dep/DB.

## Question

The user asked for "WAF / 网站监控". Recon shows these split sharply by feasibility: WAF-proper requires shipping our own engine (XL, multi-milestone, needs live traffic to verify), while website access-monitoring analytics is M–L, CI-verifiable (pure parser/aggregator), and delivers the visible value (stats, rankings, visitor map) a WAF dashboard would. What is the honest, CI-verifiable increment?

## Decision

**v1.6 = Website Access Monitoring (analytics over nginx access.log). WAF-proper is deferred** as a documented future milestone (own-engine, opt-in — will not be started without explicit user commitment, and an engine-less shim will never be presented as WAF parity). Three phases:

- **Phase 16 — Access-log parser + aggregator + store (backend core, CI-verifiable):** a tolerant nginx `main`-format line parser (pure), a bucketed aggregator (PV/UV/distinct-IP/QPS/status-class + top-N URI/IP/referer, pure), and a dedicated `website_stat.db` store with retention prune (mirrors the host-monitor subsystem). Parser + aggregator unit-tested with fixture log lines (no live nginx); store tested against a temp sqlite.
- **Phase 17 — Incremental tailer + enrichment + API (backend):** per-site offset-tracked `access.log` tailer feeding the aggregator on a schedule; agent-side GeoIP reader (copied from `core/utils/geo`, degrades gracefully); `POST /websites/{id}/monitor/stat|rank` endpoints behind the existing site auth.
- **Phase 18 — Monitoring dashboard (frontend):** a website "Monitoring" page — ECharts time-series (PV/UV/QPS/status) + ranking tables — reachable for site admins in community, gated by a genuine signal, **never forging `isProductPro`/license**.

## Security / privacy acceptance

- The M1–M6 controls in the design doc are the checklist: bound + sanitize parsed fields (log-injection M1), line-length cap + linear regex (ReDoS/DoS M2/M5), site lookup by DB row not client path (traversal M3), retention-bounded PII (M4), pinned small UA parser that degrades to "unknown" (M6). Frontend renders parsed strings as text/interpolation, never `v-html`.
- No license state is touched; the community build simply has the feature (like the branding forms and the node UI).

## Deliberately out of scope

- **WAF-proper** (engine, rules/ACL/IP-groups, attack-log store, block page, WAF frontend) — deferred; own-engine XL milestone.
- **GeoIP visitor map + UA device/browser ranking** — may split to a v1.7 enhancement (extra dep + map component + fixture-mmdb tests); v1.6 core is IP/URI/referer/status ranking + time-series.
- Live-site acceptance (a real OpenResty site generating traffic) is human UAT — the tailer is a thin I/O adapter over the CI-tested parser.
