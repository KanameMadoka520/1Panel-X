# v1.8 里程碑决策 — 社区 WAF 对齐专业版功能面

**日期：** 2026-07-26 · **作者：** KanameMadoka520 · **分支：** `open-pro-v1`
**目标功能面：** `.planning/research/WAF-PRO-PARITY.md`（用户提供的专业版截图观察记录 + 诚实性红线 R1–R7）
**依据：** 6 路并行代码侦察（网关 / agent 后端 / 前端 / geo+监控 / 社区重叠面 / CRS 引擎能力）后的架构综合。

## 前置红线（继承并加严）

本里程碑复刻的是专业版**用户可见的结果**，不是它的实现。绝不复制闭源 `1pwaf`/xpack 代码，绝不伪造授权状态，
绝不把 shim / no-op / 纯配置桩描述成「WAF 已完成」。自动化测试通过 **不等于** 人工验收通过——
用户已于 2026-07-26 明确表示暂时无法做人工验证，因此所有需要真机/浏览器的验收项一律保持 `pending`，不得回填伪造证据。

## 架构决策

### D1. 配置热重载用「网关监视 gateway.json 文件」实现，不新增配置推送端点；这是整个 Pro 对齐工作的第一优先前置。

**理由：** 当前唯一的应用路径是 writeGatewayConfig → compose Up → compose Restart → 轮询 /healthz 等 generation。一旦引入封禁与限频计数（内存态），任何一次无关设置保存都会把它们全部清空——那比专业版还差，且会逼我们写不诚实的 UI 文案来解释。文件监视方案零新增攻击面（W5 不受影响）、零新增认证问题、agent 侧的 generation 握手完全不用改（网关重载后 /healthz 自然回显新 generation）。compile-then-swap 的机制(engine.reloadRaw + atomic.Value)已经写好并有测试覆盖，只是从来没有运行时调用者。

**备选与否决理由：** (a) POST /admin/reload：需要令牌分发，且是一个可被本机任意进程触达的变更端点。(b) SIGHUP：容器内发信号要额外通道，distroless 无 shell。(c) 继续每次重启：直接导致封禁语义不成立，被否。文件监视失败时保留 compose Restart 作为回退路径。

### D2. 限频计数与临时封禁状态存在网关进程内存；不做持久化、容器重启后不重新武装；但每一次封禁/到期/解封都写 JSON 行到 audit 卷的 events.log，历史落进 waf.db。

**理由：** 容器是 read_only + cap_drop ALL + distroless nonroot，除 tmpfs /tmp(16m) 外只有 audit 绑定挂载可写。持久化实时封禁需要新增可写卷并处理陈旧封禁的重放语义——而运维重启 WAF 时多半就是想要一个干净状态。拆成「实时状态在内存 + 历史在日志」既符合容器约束，又让「封锁记录」这张表在网关重启后依然有内容。有了 P24 的热重载，状态丢失窗口从「每次保存配置」缩到「容器真正重启/升级」，这是一个可以如实写进 UI 的行为。

**备选与否决理由：** (a) 把封禁写进 waf.db 由 agent 回推：跨进程往返，封禁生效有秒级延迟，且 agent 挂了封禁就不生效。(b) 新增可写卷做快照：增加挂载与升级路径复杂度，收益是重启后恢复陈旧封禁——存疑。(c) 照抄专业版「重启 OpenResty 会解封」的文案：R3 明令禁止，那描述的是它的实现。

### D3. 网关新增的实时状态读取与手工解封走同一 listener 上的 /admin/*，用「loopback Host 检查 + 从现有只读 config 挂载读取的共享令牌」双重门控。

**理由：** 网关目前唯一端点是 GET /healthz，只做 loopback Host 检查——在 network_mode: host 下，本机任意进程（含另一个容器）都能满足这个检查。解封是安全相关的变更操作，必须再加一层。令牌文件由 agent 以 0600 写进已经存在的 ./config 只读挂载，不需要改 compose 挂载列表。WithHealth 在 Router 分发之前求值，所以 /admin 路径天然不会被任何站点路由触达（W5）。

**备选与否决理由：** (a) 只靠 loopback：不足。(b) 走 Unix socket：容器 read_only，socket 需要可写路径。(c) 把解封请求塞进 gateway.json：列表无界增长且语义混乱。

### D4. 地理能力一分为二：展示（拦截地图、IP 归属地）在控制面摄取期解析并落 CountryISO 列；执行（地区访问限制）在网关里做，需要挂 mmdb 并通过 /healthz 上报能力位。

**理由：** 展示只需要事件里已有的真实客户端 IP（applyRealIP 已经把 X-Real-IP 写进 RemoteAddr，Coraza 审计记录里的 client_ip 就是真值），零数据面改动、零打包改动，且能对历史数据回填、支持 SQL GROUP BY 出 TOP 国家。执行必须逐请求判定，只能在网关里，代价是新增依赖(maxminddb-golang，纯 Go，兼容 CGO_ENABLED=0 distroless)、新增只读挂载、以及 compose 升级路径。拆开之后展示可以先上线，执行可以独立排期，两个消费者互不阻塞。

**备选与否决理由：** (a) 全在网关做：需要替换 Coraza 自带的审计写入器才能把国家写进记录（directivesFor 只是发 SecAuditLog 指令，序列化由 Coraza 拥有，我们没有钩子），XL 且没必要。(b) 全在查询期解析：无法 GROUP BY，做不出 TOP 国家与地图，且每次请求都开 mmdb。

### D5. 「默认规则」UI 映射到真实 CRS 规则 ID 段 + SecRuleRemoveById，并额外暴露 PL 与异常分阈值；绝不转抄专业版的正则表，绝不使用 SecRuleUpdateActionById。

**理由：** 我们跑的是 CRS v4.25.0，专业版那张表是它自己引擎跑的正则——摆出来就是「显示的和拦的不是一回事」。ID 段是 CRS 保证的分组约定，升级安全；SecRuleRemoveById 支持空格分隔 ID 与 start-end 区间，对不存在的 ID 静默无操作（升级后优雅降级，配一条对账提示即可）。反之 SecRuleUpdateActionById 找不到 ID 会硬报错并使整个 coraza.NewWAF 编译失败——一次 CRS 依赖升版就能让所有站点重载失败；上游还有两个已知缺陷（非区间分支在循环里 early-return 只应用第一个 ID；按 tag/区间更新 target 时取了循环变量的地址）。PL1-PL4 与异常分阈值是专业版那 9 组没有的真实旋钮，且可用「PL2 才命中的载荷」做 CI 断言。

**备选与否决理由：** (a) 按 tag 分组(SecRuleRemoveByTag)：Coraza 的实现是精确字符串相等而非正则，且 CRS 标签是多轴的（一个文件常带多个 attack-* 标签，如 934 同时是 rce/injection-generic/ssrf/ssti），没有一个 tag 干净等于一个 UI 组。tag 适合做「单条规则的标签展示」，不适合做组键。(b) 造一张我们自己的正则表：等于自研一个弱引擎，被 WAF-ENGINE-DESIGN 的 Option D 明确否决。

### D6. 按站点的规则集通过「策略指纹 → 引擎」缓存实现，硬上限 8 个不同指纹，超限在控制面生成阶段就报错。

**理由：** router.go 现在是 engines map[Mode]*Engine，最多两个编译实例。每个不同的规则策略都是一次完整的 CRS v4.25 编译（1000+ 规则外加 21 个 .data 查表文件），内存与启动延迟都是可观测代价。绝大多数站点会共用全局默认，所以实际指纹数 = 1 + 有自定义覆盖的站点数。设硬上限并在生成配置时给出「哪几个站点需要合并策略」的可读错误，比在运行时编译 200 份规则集要诚实得多。上限是常量，实测后可调。

**备选与否决理由：** (a) 只支持全局规则策略：与专业版的【网站】徽章语义不符，且两级骨架已经建好，白白浪费。(b) Host 链式 SecRule 把所有站点规则塞进一个引擎：可行但规则数随站点线性增长且难以调试，仅用于文件上传扩展名这类小规则。(c) 不设上限：可预见的内存事故。

### D7. 自定义规则与 URL/User-Agent 名单实现为网关里的 Go 求值器，不生成 SecLang 指令。

**理由：** 首要风险不是 ReDoS（Coraza 的 @rx 走 Go RE2，线性，无灾难性回溯），而是指令注入：WithDirectives 吃的是一整个裸字符串，用户字段里一个未过滤的换行就能注入任意指令，其中 SecRuleEngine Off 会把共享该引擎的所有站点的 WAF 静默关掉。Go 求值器还顺带解决另外两个问题：(a) 不会因 per-site 规则炸开引擎缓存；(b) 可以直接写执行事件日志，而 SecLang 路径下非 CRS 判定是没有记录的。语义上这些规则是运维授权的 ACL，不是攻击检测（攻击检测由 CRS 负责），所以放弃 Coraza 的规范化变换的损失很小。求值器复用 ipACL 已验证的纪律：加载期编译、非法项硬失败、deny 优先、allow 等于可信绕过。

**备选与否决理由：** (a) 生成 SecLang：需要一个严格的序列化器 + 拒绝所有控制字符 + 编译超时，且仍要解决 per-site 与事件落地。若将来要做真正的检测型自定义规则（需要 t: 变换），可以再补，但不是这一轮的形态。

### D8. 配置契约升到 v2：网关严格拒绝未知版本；Generation 摘要覆盖整份配置而非仅 Sites 数组。

**理由：** 两个模块手工镜像同一份契约且互不 import，json.Unmarshal 又静默忽略未知字段——把新字段发给旧网关镜像，字段会被丢掉，而 /healthz 仍回显新 generation（网关回显的是它解析出来的那个），于是 waitGatewayReady 成功、面板报 Ready、UI 宣称正在执行一个根本没执行的策略。这是伪造功能状态，不是小瑕疵。严格拒绝未知版本后，旧镜像会启动失败 → 容器不健康 → 就绪超时 → 事务如实回滚报错。同理，Generation 目前只对 cfg.Sites 求哈希，任何挂在 GatewayConfig 上或作为 compose 参数的设置都不在握手范围内。

**备选与否决理由：** (a) 保持宽松版本 + 靠镜像标签管理：镜像既不由 agent 构建也不由 agent 拉取（没有 Makefile 目标），版本漂移完全靠人，不可依赖。

### D9. 一级 /waf 页面与网站详情内的 WAF 标签页并存互补，不是替代；并且使用我们自己的路由与菜单命名空间，不复用 /xpack/waf/* 与 Xpack-Menu。

**理由：** 站点标签页是运维开关站点防护的自然位置，也是诚实状态（Protected/Ready/Routed/LastError）的呈现面，删掉是功能回退；一级页面承载的是面板级视角（概览、报表、跨站点日志、封禁台账、全局策略）。两者复用同一批组件，站点页只是把作用域固定到某个 websiteID。命名空间上，/xpack 是商业分发包的地盘，把一个开源 GPL 功能塞进去既是不诚实的品牌暗示，也会在商业包被编译进来时冲突；代价只是 WebUrlMap 加几条 + 一个菜单迁移，两者我们都有现成 helper。遗留的菜单项 ID 112（Dashboard → /xpack/waf/dashboard）保持不动，那是上游的东西，改它会扩大合并面。

**备选与否决理由：** (a) 复用 Xpack-Menu 名称可以零后端改动点亮菜单（默认 LoadMenus 里已有该节点），但 Sidebar 对这个名字有硬编码特判，而且只有一个可见子项时会塌成扁平项，还得凑够两个子项——为了省一个迁移接受一堆隐式行为，不值。

### D10. WAF 总开关是真实的批量取消路由事务，不是一个布尔位；Protected 始终是所有真实信号的合取。

**理由：** R5 明确要求关闭后所有站点真的失去防护。我们已有的派生式状态（Supported && Enabled && Installed && Ready && Routed，其中 Routed 来自读取 root.conf 里 proxy_pass 的真实值）天然支持这一点：只要总开关关闭时真的把每个站点的 proxy_pass 恢复回源站，Protected 会自己变假，无需任何额外的展示逻辑。同时专业版的「生效需要全局与网站开关同时打开」正好等于我们的 AND 语义，可以如实对齐而不是勉强模仿。站点的 Enabled 意图必须保留，重新打开时按原拓扑恢复，否则运维会丢失配置。

**备选与否决理由：** (a) 总开关只停容器：站点仍指向 127.0.0.1:9000，会直接 502，是把「失去防护」做成了「站点下线」。(b) 只翻布尔位：R5 明令禁止。

### D11. CDN 真实 IP 头列表默认关闭；启用后对 X-Forwarded-For 采用「从右数可信跳数」，并在执行事件里记录 IP 的来源。

**理由：** 这是全清单里每行代码风险最高的一项。现状之所以安全，是因为只信 X-Real-IP，而 nginx 用 $remote_antaddr 覆写它（不可伪造）；X-Forwarded-For 是 $proxy_add_x_forwarded_for 追加的，applyRealIP 取最左值——那正是攻击者完全控制的位置。不加约束地信任 14 个头，等于任何客户端设一个 CF-Connecting-IP 就能绕过 IP 黑名单、临时封禁、限频计数与地区规则，并污染攻击日志。由于网关坐在 loopback 上，对端永远是 127.0.0.1，可信代理过滤只能在 nginx 层用 set_real_ip_from 做（SetRealIPConfig 已经能写），网关只能继承——这一点必须写在 UI 上而不是藏在文档里。

**备选与否决理由：** (a) 照专业版「取第一个能获取到的值」实现：直接引入绕过漏洞。(b) 完全不做：与专业版差距明显且真实 CDN 场景下 IP 归属地全错。折中方案是默认安全、启用需明示、来源可审计。

### D12. go:embed 的 compose 资产加版本标记，EnsureWafRuntimeFiles 在标记落后时重写并重建容器。

**理由：** 现状是「文件不存在才写」，意味着后续任何打包变更（geo 只读挂载、admin 令牌路径、新增命令行参数）都到不了已经部署的安装——功能在新装上能用、在老装上静默缺失，而 UI 无从分辨。这是一个会持续复发的伪造功能温床，必须在第一次改 compose 之前就把机制建好。

**备选与否决理由：** (a) 每次都覆盖：会抹掉运维的本地调整。(b) 靠升级脚本单独处理：与 agent 的运行时能力检测脱节，容易漏。版本标记是最小且自解释的方案。

## 诚实性陷阱（逐条守，实现时对照）

1. 【R1 假统计】概览的「请求 / 4xx / 5xx」。我们的攻击事件表结构上不可能产出总请求数：引擎跑的是 SecAuditEngine RelevantOnly，wafaudit.ParseRecord 还会丢弃 messages 为空的记录，只有命中规则的事务才会被写下来。诚实做法：把四个数字拆成两组分别标注来源——WAF 口径（网关侧新增的 per-site 原子计数器：已检查 / 已拦截 / 已封禁，滞后 ~0）与站点访问日志口径（WebsiteAccessStat.Pv / Status4xx / Status5xx，滞后约 1h10m 因为 PartitionClosed 会扣住未闭合的小时且 cron 是 10 分钟一跑，且只覆盖 AccessLog=true 且非 stream 的站点）。绝不能拿攻击事件数冒充请求数，也不能把两个不同人群的数字并排成一行不加说明。覆盖率不足时显示「部分站点未开启访问日志」而不是显示 0。

2. 【R2 假规则表】把专业版截图里的 9 组手写正则抄成「我们的规则表」。这既是抄闭源产物，又与我们实际执行的 CRS v4.25.0 完全不一致——显示的规则我们从不评估，真正执行的 1000+ 条规则一条都不显示。诚实做法：只展示解析自 coreruleset.FS（与编译用的是同一批字节）的真实规则，按 CRS 保证的 ID 段分组，每行显示真实 ID / msg / severity / paranoia / tags，页头写明「OWASP CRS <从模块常量读取的版本> · PL<n> · 已加载 N 条 / 已停用 M 条」，并注明这是对规则文件的解析而非引擎转储（Coraza 的公开 WAF 接口只有 NewTransaction，没有规则枚举 API）。特别地，专业版的「应用规则」组在 CRS v4 里没有对应物（应用例外已移出核心进 plugins，我们没加载），不得为了凑齐 9 组而凭空造一个。

3. 【R2 衍生 · 假的组开关】把 901/905/949/959/980/999 这些核心段做成可关闭的开关。CRS v4 是异常评分模型：单条规则只累加 tx.inbound_anomaly_score，真正的拦截决策在 949110（入站分 ≥5）与 959100（出站分 ≥4）。关掉 949/959 会让所有拦截彻底失效，而 UI 上每个攻击组仍显示「已开启」——这是最隐蔽的一类假功能。诚实做法：这些段结构性锁死（服务端对关闭请求显式报错而非静默忽略），UI 以「引擎核心（不可关闭）」块呈现并给出真实原因。

4. 【R3 假封禁语义】直接把专业版提示条「封锁 IP 临时存储在 OpenResty 中，重启 OpenResty 会解封」搬过来——我们根本没有 OpenResty 侧的封禁，那描述的是它的实现。诚实做法：用我们自己的措辞描述真实行为：封禁存在 coraza-gateway 进程内存中；配置保存不会清空（P24 热重载之后）；网关容器重启或升级会清空；历史记录留在面板数据库，可通过「拉黑」升级为永久黑名单。这段文案在 P24 落地前后是不同的，必须随实现同步改，不能先写后补。

5. 【R3 衍生 · 假的封禁状态列】封锁记录的「状态：已解封」。如果只是渲染一个固定标签，那是编的。诚实做法：状态从 events.log 的 banned/expired/released 事件推导，并与 /admin/state 返回的实时封禁集对账；对于网关重启后无法确认的历史封禁，显示「未知（网关已重启）」而不是伪造「已解封」。

6. 【R4 假地图】GeoIP.mmdb 缺失时仍渲染地图、或对解析不出的 IP 造点。mmdb 是可选的（agent 启动时后台尽力下载，失败只记日志），真实缺失场景很常见。诚实做法：网关与 agent 各自上报能力位（/healthz 加 geoip 布尔），缺失时整块灰化显示「地理库未安装」并给出安装路径；解析不出国家的事件必须以「未知」桶显示在来源表里，而不是从统计中悄悄丢掉（丢掉会让百分比加起来不等于总数）。

7. 【R5 假总开关】WAF 总开关只翻一个数据库布尔位而不真的取消路由。提示语写的是「关闭之后所有网站将失去防护」，如果站点的 nginx proxy_pass 仍指向 127.0.0.1:9000，那么防护其实还在（或者更糟，容器被停了导致站点 502——那是把「失去防护」做成了「站点下线」）。诚实做法：关闭执行真事务，把所有已路由站点的 proxy_pass 恢复回源站 + 重生成空网关配置 + nginx 校验重载 + 任一步失败全量回滚；Protected 因 isWafRouted 变假而自然翻转，无需任何展示层特判。

8. 【R6 假「应用到网站」】按钮弹一个成功提示但没有真的写入各站点策略行。诚实做法：批量写入 + 一次重生成 + 等 generation 就绪 + 失败回滚 + 按站点返回逐条结果（成功/失败/原因），部分失败要明确列出是哪些站点，不能整体报成功。

9. 【非 CRS 拦截不可见 → 过滤器是空壳】拦截记录页照抄专业版的「命中规则」过滤项（未授权域名访问 / 恶意 IP 组 / URL 规则）。当前 handler.go 里 ipACL deny 与未知 Host 都在 corazahttp.WrapHandler 之前 writeForbidden 并 return，审计日志里一个字都不会写——这些类目在我们的数据里永远是 0 条，做成下拉选项就是空壳。诚实做法：先在网关补执行事件日志（P25），让每一种非 CRS 判定都产生一条记录；过滤项只列出我们真正会写入的类目，且用我们自己的取值（CRS ruleId+msg、attack-* tag、acl-deny、ratelimit:<kind>、custom:<规则名>、unknown-host），不用专业版的规则名。

10. 【i18n 资产陷阱】社区包里已经预置了完整的 xpack.waf.* 247 键（覆盖全部 7 个标签页）以及 src/global/mimetype.ts 里的自定义规则操作符/动作/响应码下拉数据（含 captcha、五秒盾、belongToIpGroup）。字符串齐全会强烈诱使我们「反正文案都有，把开关接上去就行」。但容器是 read_only 且无会话存储，挑战页/五秒盾我们做不了；IP 组在求值器实现之前 belongToIpGroup 也无从判定。诚实做法：只接线引擎真正实现的枚举值，未实现项从下拉数据里删除或保持未接线；加一条静态检查断言前端暴露的动作集合是后端 DTO 枚举的子集，防止以后有人顺手补回来。

11. 【CDN 头列表暗示安全性】把专业版那 14 个 CDN Header 原样摆进 UI，会暗示我们能安全地信任它们。实际上 X-Forwarded-For 由 nginx 追加、最左值完全由攻击者控制，而网关坐在 loopback 上、对端永远是 127.0.0.1，无法自行判断请求是否真的来自 CDN 边缘。不加约束地启用 = 任何客户端设一个头就能绕过 IP 黑名单、临时封禁、限频计数与地区规则。诚实做法：默认关闭；启用时对 XFF 采用从右数可信跳数而非最左值；UI 明示「面板无法从当前位置验证 CDN 边缘，可信代理网段需在网站的实时 IP 设置里用 set_real_ip_from 配置」；在攻击日志里记录该条记录的 IP 来自哪个来源（对端 / 哪个头）。

12. 【站点类型覆盖范围沉默】专业版覆盖全部站点类型，我们硬性只支持反向代理站点（waf_control.go 拒绝 Type != constant.Proxy，wafconfig.Build 再校验一次）。如果一级页面的站点下拉只列出支持的站点、或对不支持的站点显示一个没有解释的灰按钮，运维会误以为自己的静态/PHP 站点被保护着。诚实做法：站点选择器列出全部站点，不支持的明确标注原因（「当前仅支持反向代理类型站点」），并在概览的覆盖率说明里给出「N 个站点中 M 个受保护」的真实分子分母。

13. 【清空/导出按钮的作用域含糊】「清空所有日志」如果只删 waf.db 行却让 UI 暗示连网关侧也清了，运维会误判。诚实做法：按钮文案与确认框明确说明清的是面板数据库里的记录，不影响网关的 audit.log/events.log，也不会解除任何现有封禁；如果要连带清理网关侧文件，那必须是另一个独立的、说明清楚的动作。

14. 【R7 人工 UAT】自动化测试全绿不等于验收通过。本计划里每个阶段都有只有真人能验的部分（原地重载不丢连接、真实流量触发限频与封禁、真机 mmdb 可读、总开关真的让站点失去防护、11 语言下的排版、地图在明暗主题下的可读性）。这些一律标 pending / human_needed，不得因为 CI 绿了就在里程碑文档里记成已完成，也不得回填伪造的验收证据。
